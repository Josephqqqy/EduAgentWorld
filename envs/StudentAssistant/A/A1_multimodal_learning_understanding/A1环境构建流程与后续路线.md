





# A1 环境构建流程与后续路线

更新日期：2026-09-15

## 1. 文档目的

本文档记录 `A1_multimodal_learning_understanding` 环境从数据准备到候选任务验证的完整构建流程，并说明下一阶段如何接入模型、执行 Agent Rollout、生成优质轨迹，以及为后续训练和 Benchmark 构建数据。

A1 当前聚焦一个明确的真实教育任务：

> 使用者上传一张数学题图片，Agent 根据用户要求识别图片中的一道或多道题，判断题目是否完整，理解文字、公式和数学图形，分析知识点，并逐题提交解答。

当前环境已经完成任务数据、工具、任务合成和候选任务 Sandbox 验证，但尚未完成真实模型驱动的 Agent Rollout。

## 2. 核心概念

### 2.1 Ground truth

Ground truth 描述图片中客观存在的内容，包括：

- 一张图片中有几道题；
- 每道题对应哪个区域；
- 题号和题目原文；
- 公式、图形和其他结构化信息；
- 识别结果应该是什么。

它主要用于验证 OCR、区域识别、完整性判断和结构化结果，不是 Agent 可直接读取的答案。

### 2.2 规范化题库

规范化题库把“图片中的一个题目区域”转换为稳定、可查询的题目对象。它将题目内容与图片文件解耦，从而支持：

- 一图多题；
- 同一道题出现在多张图片中；
- 一道题关联多个来源；
- 题目、图片区域和标准解答分别维护；
- 按学科、题型、知识点和来源查询。

### 2.3 标准解答

标准解答保存最终答案、解题步骤和关键知识点，用于隐藏评测。Agent 解题时不应看到标准解答，只能在提交答案后由 Harness 内部评估。

### 2.4 候选任务

候选任务是从工具依赖图和固定图片素材中合成的任务规格。它定义用户要求、图片参数、参考工具序列和验证要求，但不是模型已经执行过的轨迹。

### 2.5 Agent 轨迹

Agent 轨迹是模型真实执行任务时产生的过程记录，包括：

- 模型观察到的任务和上下文；
- 模型每一步选择的工具；
- 工具调用参数；
- 工具返回结果；
- 模型在步骤间的决策信息；
- 最终答案；
- 隐藏评测结果；
- token、时延和错误等运行信息。

候选任务的 `execution_plan` 只能证明任务链路可以执行，不能直接当作优质训练轨迹。

## 3. 已完成的环境构建流程

### 第一步：确定 A1 任务边界

A1 被限定为“多模态学习材料理解与解题”环境，当前主要处理数学题图片，不承担跨网站检索等 C1 类任务。

当前覆盖的典型需求包括：

1. 一张图片中包含多道题，分别解答；
2. 将题目图片转换为可编辑文本；
3. 判断图片中的题目是否完整；
4. 识别并解释数学图形；
5. 根据题目生成知识点分析；
6. 对一道或多道题提交最终答案和推理过程。

### 第二步：准备原始图片与来源信息

原始素材位于：

```text
raw/assets/
```

相关元数据位于：

```text
raw/asset_manifest.csv
raw/source_annotations.csv
```

素材清单负责记录文件路径、媒体类型、尺寸、哈希和素材状态；来源标注负责记录考试、年份、地区、题号和出处等信息。

当前图片格式按真实文件格式保存：

- `1-10`、`21-30` 为 PNG；
- `11-20` 为 JPEG，并使用 `.jpg` 扩展名。

### 第三步：进行区域级题目标注

每张图片按题目区域标注，支持一图多题。区域标注建立图片、区域和题目之间的对应关系，并为后续的 `for_each` 遍历提供依据。

区域坐标的作用是：

- 指明一道题在原图中的位置；
- 支持裁剪、区域 OCR 和图形定位；
- 验证区域检测结果；
- 防止一图多题时把不同题目混在一起。

当前 fixture ground truth 位于：

```text
fixtures/ground_truth/
```

### 第四步：建立 Ground Truth

Ground truth 保存区域级标准识别结果，作为确定性 Fixture 工具和后续真实 OCR 评测的依据。

当前 Fixture 模式不会真正调用外部 OCR 模型，而是从标注数据返回确定性结果。因此它验证的是工具接口和数据流程，不代表待测模型本身的视觉识别能力。

### 第五步：建立规范化题库

规范化题目位于：

```text
normalized/problems.json
```

题目对象保存题干、公式、题型、知识点、图形标记、来源和审核状态等信息。图片中的出现位置通过数据库关系与规范化题目关联，而不是把图片和题目写成同一个对象。

### 第六步：逐题建立标准解答

标准解答位于：

```text
normalized/solutions.json
```

它包含最终答案和可用的分步解答，是隐藏答案评测的基础。标准解答不会通过公开的题目上下文工具暴露给 Agent。

### 第七步：设计数据库 Schema

数据库结构定义在：

```text
schema.sql
```

Schema 将以下对象连接起来：

- 素材来源；
- 上传图片；
- 图片题目区域；
- 识别运行和识别修正；
- Ground truth；
- 规范化题目；
- 题目出现记录；
- 标准答案和解题步骤；
- Agent 提交；
- 审计日志。

其中最重要的职责划分是：

```text
artifact_regions              图片中有哪些题目区域
recognition_ground_truth      每个区域应识别成什么
problems                      规范化后的题目是什么
solutions                     题目的标准解答是什么
```

### 第八步：实现数据库 Seed

数据初始化逻辑位于：

```text
seed.py
```

`seed.py` 读取原始素材清单、来源标注、规范化题目、标准解答和 Ground truth，并按照 Schema 写入 SQLite。

环境入口：

```text
env.py
```

每次构建任务环境时，可以创建一套独立、可复现的数据库状态。

### 第九步：构建公开工具与隐藏评测器

工具实现位于：

```text
tools/
```

当前 Agent 可见工具如下：

| 工具 | 中文含义 |
|---|---|
| `upload_artifact` | 上传学习材料 |
| `get_artifact` | 查询学习材料 |
| `list_artifact_regions` | 列出图片中的题目区域 |
| `recognize_content` | 识别题目文字、公式或视觉内容 |
| `extract_editable_text` | 导出可编辑题目文本 |
| `assess_content_completeness` | 判断题目内容是否完整 |
| `get_problem_context` | 获取单道题的上下文 |
| `get_artifact_problem_contexts` | 获取一张图片中的全部题目上下文 |
| `analyze_diagram` | 分析数学图形 |
| `analyze_problem_knowledge` | 分析题目知识点 |
| `submit_solution` | 提交最终答案和推理过程 |

隐藏评测器：

```text
evaluate_submission
```

它由 Harness 内部调用，不注册给 Agent，从而避免泄露标准答案和评分逻辑。

### 第十步：建立工具依赖图

工具图定义在：

```text
tools/graph.py
```

工具图用于任务合成和可视化，不需要提供给执行任务的 Agent。边权含义为：

| 权重 | 含义 |
|---|---|
| `3` | 强依赖 |
| `2` | 弱依赖或推荐前置步骤 |
| `1` | 补充关系，用于增加任务路径变化 |

工具图的可视化位于：

```text
visualization/
```

可视化数据由 `tools/export_graph.py` 从 `tools/graph.py` 导出，保证代码中的工具图是唯一真实来源。

### 第十一步：随机游走并生成候选任务

任务生成逻辑位于：

```text
tools/task_generation.py
```

任务生成过程为：

```text
工具依赖图
  -> 加权随机游走
  -> 补齐必要前置工具
  -> 调整工具依赖顺序
  -> 选择固定图片 Fixture
  -> 实例化工具参数
  -> 删除无意义的重复调用
  -> 为一图多题加入 for_each
  -> 生成候选任务 JSON
```

“参数实例化”表示把抽象工具路径转换为可执行调用，例如将素材绑定为具体图片，将后续 `artifact_id` 绑定到上传结果，并将区域级调用绑定到 `$item.region_id`。

当前候选任务位于：

```text
generated/tasks_seed_42.json
```

其中 `seed_42` 表示随机种子为 `42`，用于复现同一批随机选择和路径；它不是图片编号或题号。

当前已生成 30 个候选任务，部分任务使用更长的随机游走路径。

### 第十二步：构建 Sandbox 并验证候选任务

候选任务执行器位于：

```text
sandbox/
```

Sandbox 的职责是：

- 为每个任务创建独立的内存 SQLite 环境；
- 解析前一步工具输出的参数绑定；
- 执行参考 `execution_plan`；
- 使用 `for_each` 遍历一图多题区域；
- 隔离单个任务失败；
- 隐藏标准答案和内部推理；
- 在提交后调用隐藏评测器；
- 输出机器可读的验证报告。

验证报告位于：

```text
generated/tasks_seed_42_validation.json
```

截至 2026-09-15，验证结果为：

```text
候选任务：30
通过：30
失败：0
```

这里的“通过”表示任务参数、工具依赖、数据绑定、循环遍历和隐藏评测链路可以执行，不表示某个模型已经自主完成任务。

## 5. 后续实施步骤

### 第十三步：配置模型后端

建立本地环境变量配置，至少包含：

```dotenv
AGENT_API_KEY=
AGENT_BASE_URL=
AGENT_MODEL=
AGENT_API_TYPE=openai_compatible
AGENT_TEMPERATURE=0.2
AGENT_MAX_TOKENS=4096
AGENT_TIMEOUT=120
```

建议新增：

```text
.env.example
rollout/config.py
```

配置原则：

- 真实 API Key 只保存在本地 `.env` 或系统环境变量；
- `.env` 必须被 Git 忽略；
- `.env.example` 只保存字段名和非敏感默认值；
- API Key 不得写入候选任务、轨迹、数据库或测试文件；
- 云端模型和本地 OpenAI-compatible 推理服务使用统一配置接口。

### 第十四步：实现模型客户端

建议新增：

```text
rollout/model_client.py
```

模型客户端负责：

- 将任务指令、工具定义和历史观察发送给模型；
- 支持文本模型和视觉模型的输入差异；
- 解析模型返回的工具调用或最终回答；
- 统一处理超时、限流、重试和错误；
- 记录 token 用量、延迟和模型元数据。

如果模型本身不支持图片输入，应先让 Agent 调用 OCR/识别工具获取文本；如果模型支持视觉输入，可以把图片作为任务输入，同时保留工具调用能力。

### 第十五步：定义轨迹格式

建议新增：

```text
rollout/trajectory.py
```

每条轨迹至少保存：

```json
{
  "trajectory_id": "traj_xxxx",
  "task_id": "task_xxxx",
  "model": {},
  "task": {},
  "steps": [],
  "final_submission": {},
  "evaluation": {},
  "usage": {},
  "status": "completed"
}
```

轨迹中可以保存模型决策和工具观察，但训练导出时应区分：

- 可用于监督训练的公开上下文；
- 仅供分析的运行元数据；
- 永远不能暴露给模型的标准答案和隐藏评分信息。

### 第十六步：实现 Agent Rollout 循环

建议新增：

```text
rollout/runner.py
```

核心循环为：

```text
加载候选任务
  -> 创建独立环境
  -> 向模型提供用户任务、图片和公开工具定义
  -> 模型选择工具及参数
  -> Harness 校验并执行工具
  -> 将工具观察返回模型
  -> 模型继续决策
  -> 模型调用 submit_solution
  -> Harness 调用隐藏评测器
  -> 保存完整轨迹
```

必须设置以下运行限制：

- 最大步骤数；
- 最大 token 数；
- 单次调用超时；
- 整个任务超时；
- 工具参数校验；
- 重复调用检测；
- 不存在工具的处理；
- 一图多题是否全部提交的检查；
- 异常和中断后的轨迹落盘。

模型在 Rollout 中可以看到：

```text
用户任务
图片或公开素材信息
公开工具定义
公开工具返回结果
自己的历史调用
```

模型不能看到：

```text
execution_plan
raw_walk
标准解答
隐藏评测器
隐藏 Rubric
其他模型的参考轨迹
```

### 第十七步：先运行单任务冒烟测试

不要一开始批量调用全部任务。先选择一个满足以下条件的任务：

- 单张图片；
- 一道或少量题目；
- 包含识别、上下文获取和解答提交；
- 有完整标准答案；
- Sandbox 已验证通过。

检查：

1. 模型能否正确理解任务；
2. 模型能否生成合法工具参数；
3. 工具结果能否正确返回上下文；
4. 模型能否在步数限制内提交；
5. 隐藏评测器能否给出结果；
6. 轨迹能否完整保存；
7. 隐藏字段是否没有进入模型上下文。

### 第十八步：批量 Agent Rollout

单任务通过后，再对 30 个候选任务运行一个或多个模型。

建议每个任务执行多次，因为同一模型在不同采样下会产生不同路径。每次运行应使用独立：

- `run_id`；
- 随机种子；
- 数据库实例；
- 轨迹文件；
- 评测结果。

批量运行需要支持失败重试、断点续跑、并发限制和费用统计。

### 第十九步：构建轨迹级评测

当前隐藏评测主要关注答案是否匹配以及推理是否存在。后续还应增加过程指标：

| 指标 | 说明 |
|---|---|
| 任务完成度 | 是否满足用户要求并处理全部题目 |
| 答案正确率 | 最终答案是否匹配标准解答 |
| 区域覆盖率 | 一图多题是否遗漏区域 |
| 工具合法率 | 工具名称和参数是否合法 |
| 依赖顺序 | 是否在获得必要输入后调用工具 |
| 工具效率 | 是否存在明显无效或重复调用 |
| OCR/结构化准确率 | 与 Ground truth 的匹配程度 |
| 图形理解质量 | 图形实体、关系和解释是否正确 |
| 知识点质量 | 知识点是否准确、完整 |
| 恢复能力 | 工具失败后是否能合理重试或换路 |
| 成本 | 步骤数、token、时间和 API 费用 |

工具图可以用于检查依赖合法性，但不应强迫模型完全复现参考路径。只要完成任务，模型可以采用不同但合理的工具序列。

### 第二十步：生成并筛选优质轨迹

优质轨迹不能只依据“最终答案正确”判断，还应满足：

- 用户任务全部完成；
- 没有读取隐藏信息；
- 工具参数和依赖顺序合法；
- 一图多题没有遗漏；
- 推理和答案正确；
- 没有大量无意义调用；
- 轨迹可复现；
- 人工抽检通过。

优质轨迹可以来自：

1. 能力较强的教师模型 Rollout；
2. 规则执行计划与模型解题结果的组合；
3. 人工编写或人工修订；
4. 多次 Rollout 后由评测器筛选最佳轨迹。

推荐保留原始轨迹和审核后的轨迹，避免覆盖：

```text
trajectories/raw/
trajectories/reviewed/
```

### 第二十一步：划分训练集和 Benchmark

“70% 用于训练、30% 用于 Benchmark”在逻辑上可行，但不能直接随机拆分同源图片或同一道题，否则容易发生数据泄漏。

应优先按以下实体分组后再划分：

- 原始图片；
- 规范化 `problem_id`；
- 同源试卷或来源；
- 高度相似的题目；
- 同一题的不同截图。

推荐保存为：

```text
datasets/train_tasks.jsonl
datasets/train_trajectories.jsonl
datasets/benchmark_tasks.jsonl
datasets/benchmark_references.jsonl
```

其中：

- 训练集可以包含任务和经过审核的优质轨迹；
- Benchmark 公开输入只包含任务；
- Benchmark 标准答案、参考信息和评测规则应单独保存并在评测时隐藏；
- 30 个任务适合验证流程，不足以支撑稳定训练和正式 Benchmark，后续需要扩充素材、题型和任务模板。

### 第二十二步：扩展到其他学科和真实工具

A1 流程稳定后，可以在保持工具契约的前提下扩展：

- 物理题图、实验图和受力图；
- 化学方程式、装置图和分子结构；
- 生物结构图和实验材料；
- 语文阅读材料；
- 英语听力、阅读和作文；
- 教材 PDF 或课堂讲义。

同时可以逐步将 Fixture 工具替换为真实组件：

```text
Fixture OCR       -> 真实 OCR/视觉模型
Fixture 图形分析   -> 图形检测与关系抽取模型
Fixture 知识点     -> 教育知识库或分类模型
本地固定素材       -> Harness 文件上传与对象存储
确定性评测         -> 规则评测 + 模型评审 + 人工抽检
```

替换实现时应尽量保持工具名称、参数和返回结构稳定，以便旧任务和旧轨迹继续可用。

## 6. 推荐的近期执行顺序

当前最合理的短期顺序是：

```text
1. 新建 rollout/ 目录
2. 添加 .env.example 和模型配置读取
3. 实现 OpenAI-compatible 模型客户端
4. 定义轨迹 JSON Schema
5. 实现 Agent 工具调用循环
6. 用 1 个候选任务做冒烟测试
7. 检查隐藏信息隔离
8. 对 30 个任务执行批量 Rollout
9. 增加轨迹级评分
10. 筛选和人工审核优质轨迹
11. 扩充任务规模
12. 按题目和来源分组构建训练集与 Benchmark
```

近期的第一个开发任务应是“Rollout 基础设施”，而不是立即填写真实密钥或批量消耗 API。可以先完成配置占位、模型客户端接口、轨迹格式和模拟模型测试，再接入真实模型。

## 8. 完成标准

A1 环境的第一阶段可在满足以下条件后视为闭环：

1. 候选任务能够稳定生成并通过 Sandbox；
2. 至少一种模型后端能够完成真实 Agent Rollout；
3. 一图多题可以逐题处理和提交；
4. 每次 Rollout 都能保存完整、可复现轨迹；
5. 标准答案和隐藏评测不会泄露给模型；
6. 结果正确性和轨迹质量都能量化；
7. 优质轨迹经过自动筛选和人工抽检；
8. 训练数据与 Benchmark 按题目和来源隔离；
9. 更换模型或真实 OCR 后仍能复用任务和评测框架；
10. 新增学科时可以复用同一套构建流程。
